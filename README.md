# YQG Events

A source-backed Windsor–Essex events guide, built with **Next.js App Router, TypeScript, Drizzle and Turso**. The public site, ingestion API, remote MCP server and single-owner OAuth endpoints ship as one Vercel-ready application. No deployment has been performed.

## Run locally

Use Node.js 22.12+ (Node 24 recommended).

```sh
npm ci
npm run setup:local
npm run db:migrate
npm run db:seed   # optional: six clearly labelled FICTIONAL listings; local DB only
npm run dev
```

Open <http://localhost:3000>. `setup:local` generates unique credentials in ignored `.env.local` and preserves an existing file. The generated local owner password appears only in the final comment of that file. It is not printed to terminal logs. Read it locally when testing OAuth; do not share or commit it. A clean database displays an intentional empty state.

```sh
npm run db:clear-demo   # deletes only listings marked as demo
npm run db:generate    # generate migrations after changing db/schema.ts
npm run db:migrate     # apply checked-in migrations
npm run db:studio      # optional local database editor; keep private
npm run typecheck
npm run lint
npm test
npm run build
npm start
```

Browser checks: `npx playwright install chromium`, then `npm run test:e2e`. These use a separate temporary database and start their own app server on port 3100. Core tests also use an isolated temporary database, not `.env.local`.

## What is implemented

- Responsive public calendar, search, town/category filters, today/week/weekend, free/family filters, latest-added sorting and pagination.
- Source-linked detail pages, safe Markdown (raw HTML disabled), cancellation notices, SEO metadata, Open Graph image, structured event data, sitemap and robots.
- RSS at `/feed.xml`, subscribed iCalendar at `/calendar.ics`, and per-event calendar downloads.
- Authenticated create/read/update/archive API, bounded payloads, Zod validation and atomic duplicate constraints.
- Streamable HTTP MCP at `/mcp` with six event-management tools, OAuth discovery, PKCE S256, explicit owner consent, rotating refresh tokens, scopes and revocation.
- Fictional local seed data, migration, automated tests, and a reusable collector prompt.

## Environment

| Variable               | Purpose                                                                                                                                                           |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `TURSO_DATABASE_URL`   | Local `file:local.db`, or production `libsql://...turso.io`. File databases are rejected on Vercel.                                                               |
| `TURSO_AUTH_TOKEN`     | Turso database token; blank for local SQLite.                                                                                                                     |
| `APP_URL`              | Canonical origin without a path, e.g. `https://events.example.com`. Used for OAuth audience, discovery, links and feeds. Set before building.                     |
| `EVENT_INGEST_API_KEY` | Random secret, at least 32 characters. For scripts/CLI clients, never the browser.                                                                                |
| `OAUTH_SIGNING_SECRET` | Independent random secret, at least 32 characters, used for short-lived consent tokens.                                                                           |
| `OWNER_PASSWORD_HASH`  | `salt:hex_scrypt_digest`, generated by local setup. The password is used only on the site's OAuth consent form.                                                   |
| `OAUTH_REDIRECT_URIS`  | Comma-separated **exact** client callback URLs. Default: `https://chatgpt.com/connector_platform_oauth_redirect`. Copy the exact URI ChatGPT shows. No wildcards. |

No secret has a `NEXT_PUBLIC_` prefix. Do not put credentials in a query string, collector prompt, committed MCP configuration, or browser storage.

## Turso and Vercel, when ready

1. Create a Turso database and obtain its URL and auth token. Set them in `.env.local` to migrate the remote database with `npm run db:migrate`. Back up existing data before schema changes. Migrations are not run during the Vercel build or a page request.
2. Import the GitHub repository into Vercel as a Next.js project. Use Node 24 and the default `npm run build` command.
3. Set the environment variables above for production, with fresh credentials. `setup:local` can generate the credential format in a fresh checkout. Transfer only the needed values; do not copy the local-password comment into any public place. Keep the plaintext password in a password manager.
4. Set `APP_URL` to the final production HTTPS origin. Use a separate database, credentials and canonical origin for preview deployments if you enable them. Never point untrusted branch previews at production data.
5. Deploy, test the API and OAuth connection, then create the personal ChatGPT app/plugin. All endpoints, including `/mcp`, are hosted alongside the site. There is no persistent MCP process, in-memory session dependency, or separate worker to host.

The application deliberately does not create a Vercel project, Turso database, public ChatGPT directory listing or scheduled task. Those require deployment/account setup. A personal connection does not need public directory publication.

## Connect ChatGPT

See [docs/chatgpt.md](docs/chatgpt.md) for setup, test prompts, tools, security details and the ready-to-use [collector prompt](docs/collector-prompt.md). The key distinction: a script can send the ingestion key; ChatGPT connects with OAuth. No OpenAI API key is needed by this website.

## HTTP API

All `/api/events` routes require `Authorization: Bearer <EVENT_INGEST_API_KEY>` or an OAuth access token with the appropriate scope. They return JSON and `Cache-Control: no-store`.

| Method and route              | Behaviour                                                     |
| ----------------------------- | ------------------------------------------------------------- |
| `GET /api/events`             | Paginated owner search; supports drafts and archives.         |
| `POST /api/events`            | Create; returns `201`. Defaults to `draft`.                   |
| `GET /api/events/:id`         | Read by UUID.                                                 |
| `PATCH /api/events/:id`       | Partial update; unspecified values are preserved.             |
| `PUT /api/events/:id`         | Same partial-update semantics, for spec/client compatibility. |
| `DELETE /api/events/:id`      | Reversibly archive; retains source, slug and identity.        |
| `POST /api/events/duplicates` | Check a complete candidate event before writing.              |

Search parameters: `q`, `city`, `category`, `period=upcoming|today|week|weekend|all`, `free=true`, `family=true`, `status=draft|published|cancelled|archived|all`, `sort=date|newest`, `limit` (1–100), `offset`. Default owner search includes unarchived events, even drafts. The public website and feeds independently enforce published/cancelled visibility.

Example (POSIX shell; on PowerShell use `Invoke-RestMethod` with a bearer header and JSON body):

```sh
curl "$APP_URL/api/events" \
  -H "Authorization: Bearer $EVENT_INGEST_API_KEY" \
  -H 'Content-Type: application/json' \
  --data @docs/example-event.json
```

The example is deliberately a **draft with fictional facts**, not something to publish. Required fields: `title`, `city`, `sourceUrl`, `startDateTime` with explicit UTC offset. Optional fields are defined in `lib/validation.ts`. `null` clears nullable fields. `false` means verified false; `null` means unknown. Category and tag names are flexible.

Errors: `400` invalid JSON/schema, `401` missing/invalid auth, `403` wrong scope/origin, `404` missing event, `409` duplicate/concurrent update, `413` oversized body, `429` OAuth throttling. A duplicate create includes candidate records; callers must inspect them instead of blindly retrying. A simultaneous update returns a conflict rather than silently overwriting a newer edit.

## Data conventions

- Dates are stored as UTC ISO strings and displayed/filtered in `America/Toronto`, including DST. “This weekend” is Friday through Sunday; Sunday still refers to the current weekend. “This week” ends at the next Monday midnight.
- Events stay upcoming until their end. Without a known end, they remain visible until the end of their local start day, without inventing a displayed end time.
- All-day start/end must be Toronto midnight. End is **exclusive** (a Saturday-only event ends Sunday at midnight). Calendar exports follow RFC 5545.
- Preserve the submitted source URL verbatim. The duplicate key removes tracking parameters and fragments, sorts queries, and combines normalized URL with start instant. Another unique key combines normalized title, Toronto date and city. This allows daily occurrences on a shared listing page. Multiple performances with the same title in the same city on the same day need differentiated titles (e.g. “matinee”).
- Duplicate constraints include archived events to prevent accidental resurrection by ingestion. Reuse the archived record if appropriate. Source URL matches across dates are returned for human/model review, not automatically merged.
- `published` and `cancelled` are public. `draft` and `archived` are private. Cancelled listings stay visible with a clear notice until their date passes.
- Feeds contain at most 100 upcoming listings. Source facts are never automatically fabricated or inferred by this server.
- Fictional seed data is visibly labelled, excluded from sitemap/structured event data, and cannot be seeded into a remote database by the script.

## Layout

`app/` contains pages and HTTP endpoints; `components/` the public UI; `db/` the Drizzle schema/client; `lib/events.ts` the shared event service; `lib/oauth.ts` the single-owner authorization flow; `lib/mcp.ts` the tool adapter; `drizzle/` checked-in migrations; `scripts/` setup/data utilities; `tests/` core security/data tests; `e2e/` browser tests.

The REST API and MCP tools share one validated event service rather than making loopback HTTP calls. This avoids extra serverless round trips while keeping the site independent of ChatGPT. The MCP transport uses the official SDK.

## Operating this small app

This is a private-owner integration, not a multi-user identity provider. OAuth clients may only register preapproved callbacks; login attempts and registration/token requests have persistent global limits. Tokens are opaque, hashed in the database, bound to this resource and client, and expire. Authorization codes are one-use and require PKCE. Refresh tokens rotate; sequential reuse revokes the connection family. Consent has a signed short-lived form, HTTP-only cookie, same-origin checks and framing restrictions. These measures have automated tests but are not an independent security audit. Before turning this into a multi-owner/public integration, replace the single-owner authorization component with an established OAuth provider.

Rotating the ingestion key immediately disables the old key. To revoke all OAuth connections, run `npm run oauth:revoke-all`; changing the signing secret/password alone does **not** invalidate already-issued access/refresh tokens. Expired codes/tokens and rate windows are cleaned during OAuth operations. Registered clients remain until you remove them from the database.

Public pages make no AI calls. Remote event images are displayed directly in the browser (not fetched by the server); Markdown images and raw HTML are disabled. Fonts load from Google Fonts with system fallbacks. The page also works with those remote resources blocked.
